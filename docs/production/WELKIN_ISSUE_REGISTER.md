## Confirmed Issues

### ISSUE-001: Schema Divergence Between CI Validation and Collector Runtime

| Field | Value |
|-------|-------|
| **Severity** | **P0 — Production blocking** |
| **Affected guarantee** | §4.1 Canonical event flow; §2 Functional correctness |
| **Evidence** | Two divergent CloudEvent JSON schemas exist: |

**`schemas/cloudevent.schema.json`** (used by CI `cue vet` at `validate.yaml:47`):
```json
"required": ["id", "specversion", "type", "source", "time", "data"]
```
- Does NOT require `subject`
- Does NOT enforce `specversion: "1.0"` (just `type: "string"`)
- Uses JSON Schema draft-07

**`timoni/values/collector.cue` inline JSON Schema** (the collector runtime validation source):
```json
"required": ["id", "specversion", "type", "source", "time", "subject", "data"]
```
- Requires `subject`
- Enforces `specversion: "1.0"` as `const`
- Uses JSON Schema draft 2020-12

**Impact:** CI `cue vet` could accept a canonical event that the collector would reject at runtime (missing `subject`, wrong `specversion`). This is a functional correctness violation: malformed canonical candidates could pass CI but fail at the collector boundary, or events could pass CI that the collector silently drops.

**Falsification:** A fixture with `specversion: "2.0"` and no `subject` would pass `cue vet` against `schemas/cloudevent.schema.json` but be rejected by the collector's runtime validation.

**Required outcome:** One canonical schema used by both CI validation and collector runtime, or an explicit mapping between them that guarantees equivalent strictness.

### ISSUE-002: Workflow YAML Syntax Error Breaks kubectl Installation

| Field | Value |
|-------|-------|
| **Severity** | **P1 — Important gap** |
| **Affected guarantee** | §4.7 Clean-room certification; §4.8 Bootstrap and deployability |
| **Evidence** | `.github/workflows/certification-run.yaml:54` |

```yaml
      - name: Install tooling
        run: |
          ...
          KUBECTL_VERSION: v1.36.3          # <-- this line is inside `run: |` block
          curl -LO "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl"
```

`KUBECTL_VERSION: v1.36.3` is inside a `run: |` shell block, not under an `env:` key. In bash, this is a no-op assignment (not `export`), so `${KUBECTL_VERSION}` on the next line expands to empty string. The `curl` command becomes `curl -LO "https://dl.k8s.io/release//bin/linux/amd64/kubectl"` which will fail or download the wrong binary.

**Impact:** The certification-run workflow cannot install kubectl, blocking all mock-prod certification scenarios (canonical-flow, plane-independence, producer-diversity) from executing.

**Required outcome:** Move `KUBECTL_VERSION` to an `env:` block or use `export KUBECTL_VERSION=v1.36.3` in the shell script.

### ISSUE-003: Root CloudEvent Schema Missing `subject` Requirement

| Field | Value |
|-------|-------|
| **Severity** | **P1 — Important gap** |
| **Affected guarantee** | §4.1 Canonical event flow |
| **Evidence** | `schemas/cloudevent.schema.json` vs `contracts/schema/cloudevent.cue` |

The CUE contract (`contracts/schema/cloudevent.cue:9`) requires `subject: string & != ""`. The collector's runtime schema (`engine/schemas/cloudevent.schema.json`) requires `subject` in the `required` array. The root schema (`schemas/cloudevent.schema.json`) does NOT include `subject` in `required`.

**Impact:** `cue vet -d '#CloudEvent'` in CI validates against the CUE contract (which requires subject), but the JSON schema used by the collector's `json_schema` processor also requires it. The root JSON schema used by CI is inconsistent with both.

**Required outcome:** `schemas/cloudevent.schema.json` must include `subject` in its `required` array and enforce `specversion: "1.0"` as const, matching the collector's runtime schema.

### ISSUE-004: rpk Test Failures — Two Tests Fail

| Field | Value |
|-------|-------|
| **Severity** | **P1 — Important gap** |
| **Affected guarantee** | §4.1 Canonical event flow; §2 Functional correctness |
| **Evidence** | Local test execution results |

**Test 1: `engine/tests/archive_partition_test.yaml` — test case 1 ("derives archive partition")**

Fails with: `unable to infer output type from candidates: [openmeter]`

The test references `../config/base.yaml` which contains an `openmeter` output resource. rpk (Redpanda Connect CLI) does not recognize the `openmeter` output type — it is an OpenMeter Collector-specific extension. This is expected per the architecture (`rpk` is test tooling, not production), but it means the archive partition derivation test cannot run through `rpk connect test` without config rewriting.

CI works around this by rewriting the openmeter output to a file output (`validate.yaml:49-68`), but the test as authored in the repository fails.

**Test 2: `engine/presets/kubernetes/tests/canonicalize_test.yaml` — "drops non billable kubernetes pod"**

Fails with: `wrong batch count, expected 1, got 0`

The test expects `output_batches: - []` (one batch containing zero messages), but the Bloblang mapping returns `deleted()` for non-billable pods, which produces zero output batches. The test expectation is incorrect.

**Impact:** Two test cases fail, reducing confidence in the collector pipeline's correctness. The CI workaround for test 1 adds complexity. Test 2 has a wrong expectation.

**Required outcome:** Either fix the test expectations or ensure the test harness handles `deleted()` semantics correctly. For test 1, the archive partition test now references the inlined config from `timoni/values/collector.cue` (the sole deployment source).
